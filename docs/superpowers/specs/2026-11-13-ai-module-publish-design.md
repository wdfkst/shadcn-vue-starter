# AI 对话生成模块并发布（第一版）

日期：2026-11-13
状态：待确认

## 背景与意图

上线一个业务模块目前要经过五步：评估字段和逻辑、开发、测试功能和展示、检查安全、部署到服务器。用户最近做的模块大部分是增删改查加导入导出，特殊逻辑（连表查询、计算）占比不高。

第一版只做增删改查，让页面功能和样式保持一致，把"开发"和"部署"两步省掉：用对话描述模块，生成配置，预览确认后发布，侧栏立刻出现可用页面，不改代码、不重新部署。后端最终用 Java，第一版在纯前端把流程跑通。

## 目标

- 在页面生成器里通过对话生成模块配置，配置填进现有的字段表格，可以继续对话修改，也可以手动调整。
- 预览确认后一键发布：配置存入 localStorage，侧栏立即出现菜单，打开即可真实增删改查。
- 已发布模块可以修改后重新发布，也可以下线。
- 所有模块（内置和发布的）共用同一套 Excel 导入导出：导出全部、按查询条件导出、下载导入模板、导入时逐行校验并预览错误。
- AI 接口兼容 OpenAI Chat Completions 格式，接口地址、模型名、API key 三项配置即可切换服务商。

## 非目标

- 连表查询、计算字段、审批流、状态流转。
- AI 生成源码或任何可执行代码。
- 导入时按字段匹配更新已有记录（第一版只新增）。
- 对接 Java 后端（只预留接口形状，见"以后的后端"）。

## 反目标

- AI 的输出不经过校验就生效。
- 发布前可以跳过预览确认。
- API key 出现在浏览器端代码或请求里。

## 已有基础

- `src/generator/core.mjs` 的 zod schema 定义了合法配置（`GeneratorConfig`）：模块标识、标题、描述、路由（`/business/<name>`）、字段（类型、必填、列表、查询、选项、`dictType`）。`validateConfig` 可在浏览器和服务端复用。
- `src/components/crud/CrudPage.vue` 读 `ModuleDefinition` 渲染完整增删改查页面，已支持字典联动（`dictType` 读 `systemRows.dictionaries`）、权限控制和 CSV 导出当前页。
- `src/lib/repository.ts` 的 `validateRecord` 是新增/编辑的校验规则，导入校验必须复用它。
- 菜单来自 `systemRows.menus`（localStorage `admin-data:menus`），`buildNavigation` 生成侧栏，路由守卫按菜单行的权限拦截直接访问的 URL。
- 权限由 `systemRows.roles` 的权限字符串决定，`permissionMatches` 支持 `*`、`users:*`、`*:read` 这类通配。

## 设计

### 1. AI 对话

**转发接口。** 新增 `dev/ai-proxy.mjs`，作为 Vite 插件挂在开发服务器上，提供 `POST /__ai/chat`。它读取 `.env` 中的 `AI_BASE_URL`、`AI_MODEL`、`AI_API_KEY`（不带 `VITE_` 前缀，Vite 不会暴露给浏览器），把请求原样转发到 `<AI_BASE_URL>/chat/completions`，使用 OpenAI 格式：`{ model, messages }`。响应只取文本内容返回。未配置时返回明确的 503 错误信息。

安全限制（开发服务器配置了 `host: true`，对局域网开放）：

- 只接受来自 `127.0.0.1` / `::1` 的请求，其余返回 403。
- 请求体限制 100KB，上游超时 60 秒。
- 不记录请求和响应内容。

**对话流程。** 页面生成器新增"AI 生成"面板：一个对话输入框和消息列表。系统提示词包含配置的 JSON 格式说明、当前可用的字典类型（从 `systemRows.dictionaries` 读取）、以及"只输出一个 JSON 对象、不要解释"的要求。

返回的文本去掉 markdown 代码块标记后 `JSON.parse`，再交给 `validateConfig`。校验失败时，把错误信息作为下一条用户消息发回（"上次输出校验失败：……请修正后重新输出完整 JSON"），最多自动重试 2 次，仍失败则把错误展示给用户，由用户继续对话。

校验通过的配置**不直接覆盖**当前表格：先在面板里展示差异摘要（模块名、字段列表），用户点"应用到字段表格"后才写入 `config`。之后的行为与手动配置完全一致：可以继续手动修改、预览、导出配置。

不使用各家的 JSON mode 或 function calling，只用最基本的文本补全，保证换服务商不用改代码。

### 2. 发布与下线

**适用模式。** 发布、下线和 `/business/:slug` 路由只在 mock 模式（`VITE_USE_MOCK` 不为 `false`）下启用。非 mock 模式下菜单不会写回 localStorage，后端也没有对应接口，所以生成器里的发布区域显示"发布需要后端支持，当前为接口模式"，并隐藏操作按钮。（设计者决定）

**存储。** 新 localStorage 键 `admin-published-modules`，值为 `GeneratorConfig[]`。读写复用 `readLocal` / `writeLocal`；写入返回 `false` 时（容量满或被禁用）提示"本地存储已满，发布失败"，不静默失败。

**路由。** 新增一条静态路由 `/business/:slug`，组件为 `CrudPage`，`props` 函数按**完整路由**（`config.route === to.path`）查找已发布配置，构造 `ModuleDefinition`（`endpoint` 设为 `/${key}`）。按路由而不是按 key 查找，是因为 schema 允许 key 用驼峰（`purchaseOrder`），而路由只允许小写和连字符，两者不一定相同。找不到配置时渲染现有的 404 内容。不使用 `router.addRoute`，避免刷新时路由未注册的竞态。（设计者决定）

**守卫。** 现有守卫先找菜单行的权限，找不到时退回路由的 `meta.permission`。共用路由没有按模块区分的 `meta.permission`，如果菜单行被停用或删除，守卫就找不到权限，任何登录用户都能直接打开。因此守卫需要补一条规则：`to.path` 命中已发布配置时，权限退回 `<key>:read`。这与内置模块"菜单停用后仍按模块权限保护"的行为一致。（设计者决定）

**冲突检查。** 发布时 key 和 route 都要检查：key 不能与内置模块、已生成模块、其他已发布模块重复；route 不能与任何已有菜单路径、已生成模块路由、其他已发布模块重复（同一模块重新发布除外）。

**菜单行。** 发布时在 `systemRows.menus` 追加（或更新）一行：`name` 为模块标题，`parent` 为"业务模块"，`path` 为配置里的路由，`permission` 为 `<key>:read`，`status` 为"正常"，`id` 使用 `published-<key>` 前缀以区别于手工菜单。已存在同 id 的行则更新。下线时删除该行。

**权限。** 第一版不自动改角色。管理员角色的种子权限是 `*`，因此管理员默认可访问；其他角色需要在角色管理里手动授予 `<key>:read/create/update/delete`。这与现有模块的授权方式一致。

**重新发布。** 同一 `key` 再次发布时覆盖配置。字段被删除或改类型后，已有数据行里的对应值会变成多余字段或类型不匹配。处理方式：保留数据不迁移，`validateRecord` 只校验配置里现存的字段，多余字段在下次编辑保存时自然丢弃；类型不匹配的值在编辑时按新类型重新校验，不通过就要求用户修正。发布确认对话框里提示"修改字段可能影响已有数据"。

**下线。** 生成器里列出已发布模块，提供下线操作：删除配置和对应菜单行。模块的数据（`admin-data:<key>`）保留不删，重新发布同一 `key` 时数据还在。下线前弹出确认。

**与代码生成模块的关系。** `src/modules/generated/*` 的静态路由仍然生效，且注册在 `/business/:key` 之前，因此同 key 时静态路由优先。发布时如果 key 与内置模块或已生成模块冲突，拒绝发布并说明原因（内置模块列表已在 schema 的保留字里；已生成模块从 `import.meta.glob` 的结果判断）。

### 3. Excel 导入导出

**库。** 使用 `exceljs`（MIT，浏览器端可用，支持数据验证和样式）。不使用 npm 上的 `xlsx` 0.18.5，该版本有已公开的原型污染类漏洞且修复版不从 npm 发布。导入的文件来自用户，这一点不能妥协。

**公共模块。** 新增 `src/lib/excel.ts`，函数都接收 `ModuleDefinition`，内置模块和发布模块共用：

- `exportRows(module, rows)`：生成 xlsx，表头为字段中文名，一个工作表。布尔值输出"是/否"，日期保持 `YYYY-MM-DD` 文本。
- `templateWorkbook(module)`：同上的表头，第二行起为空；另附一个"填写说明"工作表，列出每个字段的类型、是否必填、下拉字段的可选值（`dictType` 取当前字典的实时选项，否则取 `options`）。
- `parseWorkbook(module, file)`：读取第一个工作表，按表头中文名映射回字段 key，表头缺失或多余时返回整体错误。逐行校验，收集 `{ row, errors }[]`，每行报出**全部**错误。不写入任何数据。

为了报全部错误，`validateRecord` 拆出一个 `collectRecordErrors(module, input): { values, errors: string[] }`，逐字段校验并收集错误；`validateRecord` 改为调用它，有错误时抛出第一条，新增和编辑的行为不变。导入用 `collectRecordErrors`。（设计者决定）

布尔列在交给校验之前先转换："是/true/1"为真，"否/false/0/空"为假，其他值在导入层报错"只能填写是或否"。这条规则只放在导入层，编辑表单的布尔开关不受影响。日期单元格如果被 exceljs 读成 `Date`，按本地日期转成 `YYYY-MM-DD` 后再校验。（设计者决定）

**上限。** 单次导入最多 5000 行，文件最大 5MB，超出直接拒绝并说明。

**界面（CrudPage）。** 现有"导出当前页"CSV 按钮替换为下拉菜单：导出全部、导出筛选结果、下载导入模板、导入数据。导出筛选结果复用当前查询条件，但需要仓库支持取全量：`list` 增加约定，`pageSize` 传 0 表示不分页返回全部（只在 `createMemoryRepository` 实现；HTTP 仓库保持原样，按钮在非 mock 模式下禁用并提示）。

导入流程：选文件 → `parseWorkbook` → 弹出预览对话框，表格展示所有行，错误行标红并在行尾显示原因，顶部汇总"共 N 行，M 行有误"。确认后只把通过校验的行逐条 `repo.create`（受权限控制，失败则中止并报告已导入数量）。另有"导出错误行"按钮，把错误行连同原因列导出成 xlsx。

**权限。** 导出按钮要求 `<key>:read`（页面本身已要求，无需额外判断）；导入按钮要求 `auth.can(<key>:create)`，不满足时不渲染。只读角色因此只能导出。

### 4. 以后的后端

第一版所有持久化都在 localStorage，但边界按后端形状划好，方便以后替换：

- 模块配置的读写集中在一个 `publishedModules` 存取模块，替换为 `GET/PUT /api/modules` 时只改这一处。
- AI 转发接口的路径和入参（`{ messages }`）与返回（`{ content }`）固定，Java 后端实现同形状的接口后，前端把请求地址从 `/__ai/chat` 改为 `/api/ai/chat`。
- 导入导出是纯前端行为，不依赖后端；数据写入走 `Repository`，mock/HTTP 切换已有。

## 测试

- `dev/ai-proxy.mjs`：非本机来源拒绝、未配置时 503、超限请求拒绝（用 vitest 起最小 HTTP 场景或抽纯函数测）。
- 配置应用：校验失败重试逻辑抽成纯函数测试（给定响应序列，断言重试次数和最终结果）。
- 发布：发布后菜单行存在且权限正确；重复 key 覆盖；与保留 key 冲突被拒绝；下线后菜单行消失但数据键保留。
- `src/lib/excel.ts`：导出再导入往返一致；缺表头报整体错误；必填、数字、日期、字典值错误被逐行标出；5000 行上限；布尔和日期的接受格式。
- 权限：只读角色的导入入口不可用（组件测试或纯函数层断言按钮渲染条件）。

## 留给实现者决定的

- 对话面板的具体布局（侧栏、抽屉或标签页），只要不破坏现有字段表格、预览、产物三个标签。
- 系统提示词的具体措辞，只要满足"只输出 JSON、带上可用字典类型、格式与 schema 一致"。
- exceljs 的按需引入方式，以构建产物体积为准。
- 预览对话框里错误行的标红样式。
